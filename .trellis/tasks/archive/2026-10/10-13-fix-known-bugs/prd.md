# 修已知 bug（#107 像素上限 / #112 API key 复制 / 删除后 200 + 30 天缓存）

## 背景

三个缺陷，前两个来自上游 issue（长期未修），第三个是我们自己冒烟时发现的：

| # | 现象 | 来源 |
|---|---|---|
| **#107** | 上传超过 sharp 像素上限的图片时报错不友好（用户只看到失败） | 上游 issue，带 `good first issue` |
| **#112** | API key 复制不可用/复制内容不对 | 上游 issue |
| **删除语义** | `GET /i/<已删除 id>.<ext>` 仍返回 **200** + 品牌占位图，且带 `Cache-Control: max-age=2592000`（30 天） | 本仓库冒烟发现，见 `10-13-handover-baseline` 的 research |

## 目标

三处都给出「可验证的行为改变」，且不破坏既有功能。

## 范围

**In**：`backend/src/managers/image/**`（#107 与删除语义）、`frontend` 的 API key 复制组件（#112）。
**Out**：不改接口的其他语义（除非本任务明确要求）；不动 i18n 与 PR 吸收（另外两条战线）。

## 约束

- 装依赖/构建**必须 Node 20**（`export PATH=/root/picsur/.run/node20/bin:$PATH`）+ pnpm 9.6.0。
- 在自己的 worktree（`.worktrees/bugs`）里工作，不碰主工作区与其他 worktree。
- 不 push；不改 `backend/src/managers/usage/**`（遥测已定稿）。
- 改缓存头时**不要**把未删除图片的缓存也一起砍掉（那是性能特性）。

## 验收标准

- [ ] AC1 `#107`：上传超过像素上限的图片返回**明确的可读错误**（4xx，含"图片像素过大/上限"之类的信息），
      不是 500、不是静默失败；服务不崩、连接池不受影响。
- [ ] AC2 `#112`：API key 复制行为正确（复制到的是完整 key；失败有可见反馈）。
      若根因是"非 HTTPS 下 Clipboard API 不可用"，要给出可用的降级路径或明确提示。
- [ ] AC3 删除语义：已删除的 id 再取图 → **404**（而不是 200 + 占位图），
      且响应**不再带 30 天缓存**；未删除的图仍正常返回并保留原有缓存行为。
- [ ] AC4 三包构建通过；冒烟 5 步 + 7 种格式无回归。
- [ ] AC5 提交带 `[task:10-13-fix-known-bugs]` 锚点，每处修复可单独回溯（建议一个缺陷一个提交）。

## 风险

| 风险 | 应对 |
|---|---|
| 改 404 语义可能影响前端取图逻辑（前端靠占位图兜底？） | 先读 `frontend` 的取图路径确认；若前端依赖占位图，则保留占位图但改为 `404` + `no-store`，并在 PRD 记录取舍 |
| `#107` 的上限值 | sharp 默认 `limitInputPixels`；若确认是它，应在错误里写清上限与提示，并考虑做成可配置 |
