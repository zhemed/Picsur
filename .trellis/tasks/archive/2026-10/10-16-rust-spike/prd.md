# Rust 可行性试做（spike）

## 定位

**不是重写承诺**：master / 0.8.8 不动；全部工作在独立分支/目录；目标是**证明最难的部分能不能成**，并给出代价评估。

## 必须回答的risky问题（go / no-go）

1. **格式能力**：Rust 侧能否产出与现版本一致的 7 种格式（PNG/JPEG/WebP/QOI/JXL/JP2/HEIF）？纯 Rust 生态对 JXL/JP2/HEIF 薄弱，预期做法是**绑 libvips**（`vips` crate 或 FFI）—— 需要证明能编进镜像、能从 Rust 调到、且转码结果与现版本一致（可用现有 34 项回归的夹具与断言口径比对）。
2. **存储形态**：改用 **SQLite**（单体自托管足够）替代 Postgres：迁移/事务/并发写能否满足；数据文件与图片放 `./data`；给出与现在"图片存库(bytea)"的取舍建议（推荐元数据入 SQLite、图片落文件系统 ✗→ ✓）。
3. **交付形态**：单个静态二进制（musl）+ 极小镜像（distroless/scratch 级）；体积、内存、冷启动各是多少（对比现版本：镜像 803MB / all-in-one 内嵌 PG 684MB 级别）。
4. **手感**：图片以**原生 `<img src>`** + 正确 `Cache-Control` 提供（不带 blob ✗）；首屏与滚动的主观与客观（TTFB、图片加载）对比现版本。
5. **加分项（能否兑现你最初的痛点）**：单二进制是否让"面板一键升级"变成**不需要挂 docker.sock**（替换文件 + 重启进程）—— 若成立，这就是比现在更干净的终态。

## 边界

- 只在 `experiments/rust`（或独立目录）里做；**不改 master**、不动 `frontend/`、`backend/`、`support/`、`.github/`；不发布镜像。
- 允许引入 Rust 工具链与依赖（记录版本）；允许起独立容器/端口做对比测试，**不碰常驻实例与用户的卷**。

## 验收

- [ ] AC1 最小可跑服务：上传一张图 → 取回（含一种转换参数）→ 数据落在 `./data`。
- [ ] AC2 7 种格式至少**全部能编能解**（用现有夹具验证），并说明与现版本的差异。
- [ ] AC3 单二进制/极简镜像的体积、内存、启动数据。
- [ ] AC4 与现版本的关键指标对比（体积/内存/首字节/图片加载）+ 结论与迁移代价初评。
